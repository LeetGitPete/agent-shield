# Architecture diagram: node panel that fits, with notes per node and connection

**Status:** ready-for-agent
Date: 2026-10-03

## Problem Statement

The interactive architecture diagram is a page generated by the Archify skill from the diagram's JSON source. Clicking a node opens the node panel: a floating card over the diagram (Archify calls it the passport or relationship lens) with the node's title, sublabel, type, tag, id, source links, reach controls and the list of its connections.

Two problems for someone reading the diagram:

1. The panel has no height limit, and the diagram area clips anything that runs past its edge. Busy nodes have up to three source links and many connections (API, Triage, Detector), so their panel runs past the bottom of the diagram area. The lower part, usually the connection list, is cut off and cannot be reached.
2. The panel only repeats what the node already shows. There is nowhere to read a little more about what a node does, why it is built that way, or what each connection carries. Archify's source format has no field for it: components and connections reject unknown fields.

## Solution

A small patch step that runs after every Archify render. Archify, the skill's template and the diagram's JSON source stay unchanged.

After rendering the page with Archify, the maintainer runs one patch script. It:

- Caps the node panel at the visible height of the diagram area. The node title and the panel's buttons stay pinned and the rest of the panel scrolls.
- Widens the panel on desktop so one-liners fit.
- Shows 2–4 one-liners for the clicked node under its title.
- Shows 1–2 one-liners for each connection under that connection's row in the panel's connection list. The same connection's notes appear in the panels of both nodes it joins.
- Removes one known comment line from the template's viewer code.

The notes live in their own JSON file beside the diagram's source, keyed by node id and connection id. The script stops with an error, without writing the page, when the notes file and the diagram's source disagree on which nodes and connections exist.

## User Stories

1. As a reader of the architecture diagram, I want the node panel to stay inside the visible part of the diagram area, so that no part of it is cut off.
2. As a reader, I want the panel's content to scroll when it is taller than the space available, so that I can reach the source links and connections of busy nodes such as API, Triage and Detector.
3. As a reader, I want the node title and the panel's buttons (close, copy) to stay visible while I scroll the panel, so that I always know which node I am reading and can close the panel at any time.
4. As a reader, I want a panel whose content fits to look the same as before, without a scrollbar, so that small nodes are not cluttered.
5. As a reader, I want the panel to still sit next to the node I clicked, so that the link between the node and its panel is obvious.
6. As a reader on a desktop screen, I want the panel a little wider (about 26rem instead of 22rem), so that most one-liners fit on one line.
7. As a reader on a desktop screen, I want the widened panel to keep clear of the diagram's own controls on the right, so that zoom and navigation stay usable.
8. As a reader on a phone, I want the panel to keep its current full-width mobile layout, so that nothing about the mobile view gets worse.
9. As a reader, I want 2–4 short one-liners under the node's title and sublabel, so that I can learn what the node does without opening the code.
10. As a reader, I want those one-liners to cover how the node works, the key design choice behind it and how it behaves on failure, so that the panel answers the questions a newcomer actually asks.
11. As a reader, I want the node notes above the type and tag chips and the source links, so that the explanation is the first thing I read.
12. As a reader, I want 1–2 one-liners under each connection in the panel's connection list, so that I understand what travels along it and under which guarantee.
13. As a reader, I want a connection's notes in the panels of both nodes it joins, so that I see them whichever end I clicked.
14. As a reader, I want connection notes always visible, without an extra click, so that reading them costs nothing.
15. As a reader, I want clicking a connection row to keep highlighting that connection on the diagram, so that the notes do not break an existing interaction.
16. As a reader, I want the notes to switch when I click another node, so that a panel never shows a previous node's notes.
17. As a reader, I want the notes gone when I close the panel and back when I reopen it, so that the panel behaves the same every time.
18. As a reader, I want notes for every node, including the operator and the Gemini API outside the cluster, so that no node is a dead end.
19. As a reader, I want notes for every connection, so that no row in the connection list is unexplained.
20. As a reader, I want the notes in the panel's own muted small type, following the page's light and dark themes, so that they look like part of the panel.
21. As a reader, I want the notes to describe the system as the code builds it, so that I can trust what the panel says.
22. As a reader, I want the notes to add to the node's sublabel and tag rather than repeat them, so that every line tells me something new.
23. As a reader, I want the Copy button, the node search and the image export to work as before, so that the notes do not change their output.
24. As a reader using the guided views, I want them to keep working, so that the step-by-step views are not affected by the panel change.
25. As the maintainer, I want the notes in one JSON file keyed by node id and connection id, so that I edit text in one place instead of in the generated page.
26. As the maintainer, I want one command after each Archify render to reapply the panel fix, the notes and the comment removal, so that a re-render never silently loses them.
27. As the maintainer, I want the script to stop and name every node and connection that has no notes, so that I notice when I add one to the diagram and forget its notes.
28. As the maintainer, I want the script to stop and name every id in the notes file that the diagram does not have, so that renamed or removed parts do not leave stale notes behind.
29. As the maintainer, I want the page left untouched whenever the script stops with an error, so that the committed page is never half patched.
30. As the maintainer, I want the script to stop with an error when the page lacks the panel markup it hooks into, so that an Archify update that changes the panel is noticed instead of silently producing a page without notes.
31. As the maintainer, I want running the script twice to be harmless, so that I never have to remember whether I already ran it.
32. As the maintainer, I want running the script after editing the notes to replace the previous notes, not add a second copy, so that changing a note is just edit and rerun.
33. As the maintainer, I want the template comment line removed on every run, so that I do not have to delete it by hand after each render.
34. As the maintainer, I want the diagram's JSON source left unchanged, so that Archify's validation and delivery keep working on it.
35. As the maintainer, I want the installed Archify skill left unchanged, so that skill updates and other projects' diagrams are unaffected.
36. As the maintainer, I want the script to need nothing beyond Node's built-in modules, so that it runs anywhere Archify runs, with no install step.
37. As the maintainer, I want the script's usage written at its top, so that I can rerun it months from now without searching for instructions.

## Implementation Decisions

### Where the change lives

- A post-render patch step in the repository, beside the diagram. The Archify skill (template, renderer, schema) is not modified and no change is proposed upstream.
- The diagram's JSON source is not modified. Archify's schema rejects unknown fields on components and connections, so notes cannot live there.
- The committed page is always an Archify render followed by the patch script, never hand edited.

### Notes file

- A JSON file beside the diagram's JSON source, holding two maps: nodes (component id to a list of one-liners) and connections (connection id to a list of one-liners).
- Node entries hold 2–4 one-liners and connection entries 1–2. These counts guide the writing; the script does not enforce them.
- Each one-liner is plain text, with no markup and no links.
- Every component and every connection in the diagram's source has an entry: 15 nodes and 16 connections at the time of writing.

### Patch script

- A Node ES module beside the diagram, using only Node's built-in modules. It takes no arguments and works on this repository's page, diagram source and notes file. Its usage is described in a comment at its top: render with Archify, then run the script.
- It is run by hand after every Archify render. No developer-script command and no CI step are added.
- Order of work:
  1. Read the page, the diagram's source and the notes file.
  2. Check ids in both directions: every component and connection in the source has notes, and every id in the notes file exists in the source.
  3. Check the page still contains the panel markup the notes code hooks into: the panel, its title, its sublabel line and its connection list.
  4. On any failure, print every problem grouped by kind (missing node notes, missing connection notes, unknown node id, unknown connection id, missing panel markup), exit with a non-zero code and leave the page unwritten.
  5. Remove the template comment line, if present.
  6. Insert, or replace if already present, one style block and one script block, each delimited by marker comments. The script block embeds the notes.
  7. Write the page.
- Running it again on a patched page with unchanged notes produces an identical page.
- The template comment line is the one-line comment that introduces the viewer's `openExport` auto-open code. It is matched by its leading text and its `?openExport=1` ending, not by its full text. If it is absent (already removed, or reworded by a later Archify version), the script skips this step without error.

### Panel fit

- The panel's height is capped at the visible part of the diagram area: where the diagram area and the browser window overlap, minus the panel's existing margin from the edges. This is the same visible area Archify already uses to place the panel, so with the cap the panel always fits there.
- The node title and the panel's buttons (close, copy, and the connection-list toggle on mobile) stay pinned at the top. The rest of the panel (sublabel, notes, chips, source links, summary, reach controls, connection list) scrolls inside the panel.
- When the content fits, there is no scrollbar and the panel looks as it does today.
- Desktop width goes from 22rem to about 26rem, still limited by Archify's existing rule that keeps room for the diagram's controls on the right. The mobile layout (720px and narrower) keeps its current full width. On mobile the connection list stays collapsed by default, so connection notes show once the list is expanded.

### Notes on the page

- A small script, inserted after Archify's viewer code, reads the embedded notes and follows the panel: when the panel opens or switches to another node, and whenever Archify rebuilds the connection list.
- Node notes appear directly under the node's sublabel, above the type and tag chips.
- Connection notes appear directly under their row in the connection list. The row is identified by the connection id Archify puts on it. The row's own click behavior (highlighting the connection on the diagram) is unchanged.
- Notes use the panel's existing theme variables (muted text colour, small size), so they follow light, dark and every Archify preset. Each one-liner is its own line.
- Notes never appear on the diagram itself, on connection hover, in the Copy button's output, in the node search or in image export.

### Writing the notes

- The implementer writes every note from the code at the current HEAD. A note states only what the code does: no plans, no guesses.
- Node notes cover, as the node allows: how it works, the key design choice, and behaviour on failure or under load. Nodes outside the cluster (the operator and the Gemini API) and the mock provider may need only 2 lines.
- Connection notes cover what travels along the connection and the guarantee it carries: acknowledgement, retries, at-least-once, polling interval, opt-in.
- Notes add to the node's sublabel, tag and connection label and do not repeat them. They follow the diagram's existing wording style: sentence case, no trailing full stop, the same terms as the cards and labels.
- No separate review step: the maintainer approves the notes as part of approving the commit.

## Testing Decisions

- No automated tests are added. The script's own checks run on every invocation: ids in both directions and the presence of the panel markup. They catch the realistic failures, stale notes and an Archify update that changes the panel. The rest of the script is a few lines of string handling, and one run shows it works.
- Verification is running the script on the current page, then opening the page in a browser and clicking nodes: a busy node's panel scrolls with the title pinned, node notes appear under the title, connection notes appear under their rows, and both change when another node is clicked.
- If tests are added later, they should exercise the patch step as a whole (page, source and notes in; patched page or named errors out), not its internals. There is no prior art in the repository: the existing tests are the Go tests and the console's vitest suite.

## Out of Scope

- Any change to the installed Archify skill, and any upstream change to Archify.
- Any change to the diagram's JSON source: components, connections, layout, labels, cards or guided views.
- Re-rendering the diagram. The script patches the current page as it is.
- Notes on the diagram itself or on connection hover; notes in the Copy button's output, the node search or image export.
- Changes to the mobile panel layout beyond what the height cap implies.
- A developer-script command, a CI step or automated tests for the patch script.
- README changes.

## Further Notes

- A later Archify version may change the panel markup. The script's markup check then stops with an error, and the notes code needs adjusting to the new markup.
- The notes describe the system at the time they are written. When a change to the code changes what a node or connection does, its notes are updated in the same change, together with the diagram's source if that changes too.
- Archify pins a repository revision in the diagram's source for its source links. The patch step does not touch it.
